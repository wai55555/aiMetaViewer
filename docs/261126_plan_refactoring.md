## §0 前提指示（最初にここを読むこと）

1. 本書を §0 から最後まで読み、§2 の設計原則と §3 の切り捨てリスト（非対象）を
   変更しないこと。非対象に挙げた項目は「ついで対応」「将来のための先行実装」を
   含め、一切実装しないこと。実例や新情報で判断を変える必要があると考える場合は、
   実装せず PR 説明に根拠を書いて停止すること。
2. 本書の数値（バイト数、行数、予算値）は 2026-11-26 時点の `main`（v1.8.0、
   merge commit `f114ec0`）の実測である。着手時に実測と食い違う場合は、Phase 0 の
   記録に差分を残し、本書の相対関係（大小・比率）が保たれる範囲でのみ追随すること。
   相対関係まで変わる場合は実装せず報告すること。
3. ビルド工程を導入しない。現行どおりプレーンな JavaScript ファイル群を
   `extension/` に置き、 unpacked 拡張としてそのまま読み込める構成を維持する。
   bundler / TypeScript / npm 依存の追加は禁止する（§3 CUT-10）。
   `package.json` も原則として追加しない（テスト実行は §12 のコマンド直指定とする）。
4. 既存テストは `node --test tests/metadata/*.test.cjs` で実行する。変更した
   JavaScript ファイルは全て `node --check <file>` を通すこと（§12）。
5. コミット規約は §13 に従う：1 フェーズ = 1 PR、欠陥・要件 ID 単位で対応テストと
   同一コミット、各コミットでテスト緑を維持する。
6. 既存の取得層の設計（Range head 取得、形式別 head budget、同時実行ゲート、
   negative cache の版数管理、`suggestedSize` による段階的拡大）は完成度が高く、
   本計画の対象外である。§5.4 に挙げた点以外では触らないこと。
7. 対象ブラウザは Chrome / Chromium 系とする。手動確認（§11.4）も Chrome で
   行う。現行コードの Firefox 向け抽象（`browserAPI` 等）は、現行挙動を
   壊さない範囲でベストエフォートとし、本計画の各要件の完了条件には含めない。
   `chrome.scripting` や `DecompressionStream` の Firefox 側挙動の差異は、
   差異が判明した時点で §14 に記録すること。本計画が前提とする API
   （`chrome.scripting` 等）により、最低対応バージョンは
   **Chrome 95 以降**を前提とする（`executeScript` の `world` プロパティが
   95+ で追加されたため。`storage.local.getKeys()` にはフォールバックが
   あるため下限を決めない）。
8. 判断に迷う場合は「negative（メタデータを持たない画像）のコストを増やさない」
   側に倒すこと。これが本計画全体の優先規則である（§2 原則 P-1）。

## §1 背景と目的

### 1.1 現状認識（実測、v1.8.0）

| 対象 | 実測 | 問題の所在 |
|---|---|---|
| content script 注入量 | JS 13 本・330,256 bytes + CSS 9,157 bytes = 計 339,413 bytes（約 339KB）、全ページ・全フレーム・`document_start` | 画像のないページや対象外サイトでも毎回パース・実行される |
| Service Worker 起動時ロード | `importScripts` 分 527,432 bytes（pako 238,805、JSZip 97,630、parser 76,296、png_metadata_scanner 68,156、video_parser 42,628、video_range_reader 3,917）+ background 本体 224,634 bytes = 計 752,066 bytes（約 752KB）を同期ロード | MV3 の SW はアイドルで停止するため、再起動のたびに全量パースが走る |
| `background.js` | 4,846 行の単一ファイル。非 PNG head 処理が Range／full fetch／`file://` の 3 経路に重複 | 形式追加・修正のたびに複数経路への手入れが必要 |
| PNG パーサ | `parser.js` の一括版 `extractPngMetadata` と `png_metadata_scanner.js` の stream 版が併存 | 二重保守。検知仕様の差異が温存される |
| Stealth PNG | 通常メタデータがある場合でも IDAT の画素展開を伴う検証が走り得る。展開上限は 512MB（`MAX_DECODED_BYTES`） | 大半が Stealth を持たない PNG に対して最も重い処理が残っている |
| 検知担体 | PNG `zTXt` 完全未対応（リポジトリ内に文字列自体がない）、JPEG は APP1-EXIF のみ（COM・APP1 XMP 未対応） | §6 のゲート付きでのみ追加する |

### 1.2 本計画の目的

1. 通常ページ（メタデータを持つ画像がないページ）の固定コストを、§5 の
   測定可能な目標値（常駐注入量・SW 起動時ロード量）まで下げる。
2. SW コールドスタートの固定費を下げる。
3. 検知担体の追加は「negative コストがほぼゼロにゲートできるもの」だけに限定し、
   それ以外は §3 の通り明確に切り捨てる。切り捨ての判断自体を本書に記録し、
   将来同じ議論を繰り返さないことも目的に含む。
4. 重複実装を解消し、以後は「1 担体 = 1 実装箇所」の状態にする。

### 1.3 本計画でやらないことの要約

Adam7 Stealth、JPEG XL / HEIC / GIF / TIFF 対応、JPEG head budget の引き上げと
SOS 以後の探索、PNG trailing のための追加ネットワーク取得、Extended XMP の
再構成、AVIF の XMP アイテム対応。これらの詳細と理由は §3 に記す。

## §2 設計原則

- **P-1（negative 最優先）**: Web 上の画像の大半は生成メタデータを持たない。
  最適化の主対象は positive の高速化ではなく、negative の棄却コストである。
  新しい検知は「negative に課金されない」形でのみ追加できる。
- **P-2（重さの 3 分類）**: 処理の重さは次の 3 種に分けて評価する。
  - A: 種別判定（チャンク／マーカーの型を見るだけ。既存の走査に相乗りできる）
  - B: 本文の展開・デコード（キーワード・パターン・サイズでゲート可能）
  - C: 追加のネットワーク取得、または画素デコード（negative 全体に課金される）
  追加してよいのは A のみ、または B をゲートで negative 無料にできるものだけ。
  C を伴う追加は原則禁止し、例外は §6.4（取得済みデータへの trailing 相乗り）の
  ように「追加取得が発生しない」場合に限る。
- **P-3（ゲートの 3 条件）**: 検知担体の追加は次の全てを満たす場合に限る。
  (1) negative コストをゲートでほぼゼロにできる、(2) 実例または自前書き込みとの
  整合性など具体的な必要性がある、(3) 誤検出ゲート（キーワード許可リスト、
  内容パターン、サイズ上限のいずれか）が作れる。
- **P-4（positive 限定コストは許容）**: モーダル表示時など、メタデータが既に
  見つかった画像に対してのみ発生する処理（表示整形、生成元解釈）は、
  P-1 の対象外として通常の品質基準で実装してよい（§9 Phase 6）。
- **P-5（ゼロビルド維持）**: §0-3 のとおり。軽快化のためにビルド工程を持ち込む
  ことは、それ自体が保守コストとして却下する。
- **P-6（既存の確定状態を壊さない）**: `empty-confirmed`（空の確定）と
  `unresolved`（未確定）の区別は検出率と無駄な再取得の両方を支えている。
  budget 到達や未対応を `empty-confirmed` に倒す変更は禁止する。
- **P-7（切り捨ては仕様として記録する）**: 「対応しない」ことは欠陥ではない。
  §3 の各項目には再検討条件を併記し、条件を満たさない限り再提案しない。

## §3 切り捨てリスト（非対象）

以下は本計画および将来の通常改修の非対象である。各項目の「再検討条件」を
満たす実例が提示された場合にのみ、別計画として起案できる。

| ID | 項目 | 切り捨ての理由 | 再検討条件 |
|---|---|---|---|
| CUT-01 | Stealth PNG の Adam7（インターレース）対応 | 生成系は全て非インターレース。Stealth × Adam7 は意図的に作った場合以外ほぼ存在しない。対して 7 パス行再構成は画素デコードの中で最も実装・テストコストが高い | Adam7 + Stealth の実ファイルが提示されること |
| CUT-02 | JPEG XL / HEIC / HEIF / GIF / TIFF / BMP 対応 | AI 形式としてマイナーなだけでなく、HEIC・TIFF はブラウザが `<img>` で表示できず、JPEG XL は Chrome がサポートを削除済み。拡張が遭遇する機会自体がない。対応先があるとすればローカルツール（fast_meta 等）である | 対象ブラウザが当該形式をネイティブ表示し、かつ AI 生成の流通実例があること |
| CUT-03 | JPEG head budget（256KB）の引き上げ、および SOS 以後の探索 | SOS 以後はスキャンデータしかなく探索対象が存在しない。budget を上げると、ICC/XMP が巨大な非 AI の写真系 JPEG の negative 確定コストが増える逆進性がある。段階的拡大により通常 JPEG の実コストは上限値より十分小さい | 256KB 超の位置に生成 EXIF がある実ファイルが提示されること |
| CUT-04 | PNG trailing 検出のための追加ネットワーク取得 | trailing の有無の確定には末尾 Range が negative 全件に必要になり、C に該当する。頻度も規格外の書き込みで極めて低い | §6.4 の相乗り範囲を超えて必要とする実例が複数提示されること |
| CUT-05 | Extended XMP（`xmpNote:HasExtendedXMP` の再構成） | 複数 APP1 に分割された XMP の再構成は状態管理が重く、生成メタデータを Extended 側に置くツールが確認できない | Extended 側に生成情報がある実ファイルが提示されること |
| CUT-06 | AVIF の XMP アイテム対応、および meta ボックスの後方探索拡大 | XMP アイテム収集は iinf/iloc 処理の拡張が必要で、かつ head budget 256KB のため後半の meta に届かない問題とセットであり、費用に対して AVIF + XMP の実例が乏しい | AVIF + XMP の実ファイルが提示されること |
| CUT-07 | EXIF MakerNote（0x927C）の解釈、XPComment / XPDescription 等の網羅的タグ収集 | MakerNote はメーカー固有で生成情報の担体ではない。XP 系は AI 用途の出現率が低い。本計画では §6.5 の `Software` 追加のみを行う | 当該タグに生成情報がある実例が提示されること |
| CUT-08 | zTXt の無条件展開（キーワードを見ずに全て inflate する実装） | §6.1 のゲート付き実装のみ許可する。無条件展開は B を negative に課金する形になるため禁止 | （再検討しない。ゲート付きが正解である） |
| CUT-09 | JPEG COM の無条件採用（内容を見ずに全てメタデータとして表示） | COM は GIMP やエディタの一般コメントでも頻出する。§6.2 の内容ゲート付きでのみ採用する | （再検討しない） |
| CUT-10 | bundler / TypeScript / npm ビルド工程の導入 | §2 P-5。生成物の管理とビルド再現性の保守コストが、得られる軽量化を上回る | 拡張の規模がプレーン JS の手管理限界を超えたと判断されること |
| CUT-11 | XMP の完全な XML パーサ（DOMParser 等）導入 | 重量級で、XML 特有の攻撃面も持ち込む。§6.6 の文字列レベルの限定的改善のみ行う | 正規表現系で取りこぼす XMP 実例が複数提示されること |
| CUT-12 | 一定規模を超える画像への Stealth 候補処理 | §7 の画素数上限を超える画像は Stealth 対象から外す（テキストチャンク検出は継続）。巨大画像の全画素展開は negative コストの最大要因であるため | 上限を超える Stealth 実ファイルが提示されること（§7.3 の決定ゲート参照） |
| CUT-13 | pako.js から DecompressionStream への移行 | 有効データの出力は一致するが、scanner / parser の同期 API を維持できず、破損・切断時の診断カテゴリも一致しない（`docs/pako-gate-phase2.md`） | scanner API の非同期化を認める別計画が承認され、破損時診断の対応表と §11.3 のテスト変更が先に追加されること |

## §4 全体構成（目標形）

### 4.1 content script の構成

現行：13 本を全ページへ `document_start` で注入（§1.1）。
目標：常駐は最小ローダのみとし、残りは場面別に遅延注入する。

| 区分 | ファイル（現行名） | 注入タイミング（目標） |
|---|---|---|
| 常駐（最小） | `settings_loader.js`、`content.js`（縮小後）、`badge_controller.js` | 現行どおり content_scripts で注入。ただし `content.js` から場面限定コードを分離し、常駐分のみ残す |
| 遅延 A | `ui.js`、`comfyui_parser.js` | バッジのクリック等、モーダル表示が確定した時点 |
| 遅延 B | `scanner.js` + `scanner/*.js` 一式 | 拡張アイコンのアクションで全ページスキャンが起動した時点 |
| 条件付き | `adapters.js` | 対象ホスト（現行アダプタが対象とするサイト群）に一致するページのみ |

遅延注入の実行主体と方式は次のとおりとし、代替方式は採らない：

- 注入は **Service Worker** が行う。`chrome.scripting` は content script から
  呼べないため、content 側は「モジュールが必要になった」ことをメッセージ
  （`{ action: 'ensureModule', module: '<キー>' }`）で SW に通知し、SW が
  送信元（`sender.tab.id` と `sender.frameId`）を対象に
  `chrome.scripting.executeScript({ target: { tabId, frameIds: [frameId] },
  files: [...], world: 'ISOLATED' })` で注入する。注入完了・失敗は
  メッセージの応答で content 側へ返す。
- `module` の値は SW 内の固定対応表のキーとしてのみ解釈する。対応表に
  含めるのは content 経由で要求される遅延 A（キー `ui`）のみとし、
  遅延 B はこの経路を使わない（下記）。SW はメッセージに含まれる
  ファイル名やパスを一切使わず、対応表にない値は注入せず診断を出すこと。
  あわせて SW は注入前に、対象タブが除外サイトでないことを、設定の保存先
  （除外リストのストレージキー。**Phase 1 の PR で特定し記録すること**）
  を直接参照して自ら確認すること（content 側の自己申告に依存しない）。
- 遅延 B（scanner）は content 経由ではなく、拡張アクションのイベントを
  受けた SW が、イベント引数の tab を対象に直接 `executeScript` する。
  この際の target は **`allFrames: true`** とし、全フレームへ注入する
  （現行の `all_frames` 相当。デフォルトのトップフレームのみにすると
  iframe 内画像がスキャンから漏れる）。B についても競合防止は SW 側を
  正とし、SW は tab 単位で注入中 Promise を保持して並行要求を合流させる
  こと（アクションの連続クリックで二重注入しない）。
- 注入の競合防止は SW 側の記録を正とする。SW は (tabId, frameId, module) を
  キーに注入中 Promise を保持し、並行する同一キー要求を合流させる
  （バッジの連続クリック等で二重注入が起きないこと）。役割分担として、
  content は自フレームの注入済みフラグが立っている場合は `ensureModule` を
  送らない（SW 再起動で SW 側記録が消えても再注入にならないための経路）。
  SW 側記録の役割は同一生存期間内の競合防止に限る。終了したタブ／フレームの
  記録の破棄は任意とする（SW 再起動で消えるため必須としない）。
- 遷移レースの防止は、注入コードの実行開始時に行う。**この照合は
  遅延 A の注入コードにのみ適用する**（遅延 B はメッセージ経由ではなく
  比較対象の `sender.url` が存在せず、`allFrames` の各サブフレームの
  `location` はタブの URL と一致しないため、B では照合を行わない）。
  注入されるコードは先頭で自フレームの `location` を、要求時点の URL
  （`sender.url`）と照合し、不一致なら初期化せずに終了すること
  （追加の権限が不要で、確認と注入の間の TOCTOU も実質解消できる）。
  照合は **hash を除いた URL**（origin + pathname + search）で行う。
  注入済みフラグは照合を通過した後にのみ立てること（不一致で中止した
  フレームにフラグだけが残り、以後の再試行が抑止される事態を防ぐため）。
- `web_accessible_resources` 経由の `<script>` 挿入は採用しない。当該方式は
  ページの MAIN world で実行され、分離ワールドの保護と拡張 API を失い、
  ページ側 CSP にも左右されるため等価な代替にならない。あわせて
  `web_accessible_resources` の対象を JS ファイルへ拡大しない
  （全サイトから取得可能になることによるフィンガープリント面の拡大を避ける。
  現行どおり `icons/*` のみとする）。
- `scripting` パーミッションの追加は Phase 1 の最初の判断ゲートとする。
  追加の可否と根拠（Web Store 審査・インストール時警告への影響、
  既存の `activeTab` + `host_permissions` で代替可能かの検討結果）を
  Phase 1 の PR に記録し、追加不可と判断した場合は注入方式自体を再設計する
  仕様改訂 PR を先に出すこと（安易な代替方式へのフォールバックは禁止）。
- `adapters.js` の条件付き化は scripting を使わず、manifest に第 2 の
  content_scripts エントリ（対象ホストの `matches`）を追加する方式を
  第一選択とする。対象ホスト一覧の正本はこの manifest エントリとし、
  パスやページ種別などの細かい条件は読み込み後の実行時判定に残す。
  第 2 エントリの `run_at` / `all_frames` は現行エントリと同一にする。
  Phase 1 の PR には、現行 adapters の対象ホスト・条件の一覧と manifest
  エントリへの対応表、および現行の単一リストで adapters より後ろに並ぶ
  ファイルが adapters のグローバルを読み込み時に参照していないことの
  棚卸し結果を添付すること。
- 二重注入防止はフレーム側の注入済みフラグを補助として使い、SPA の
  画面遷移後も同一フレームへ再注入しない（競合防止の正は SW 側の記録。
  上記 bullets 参照）。
- 注入失敗時（フレーム消滅、権限不足等）は、content 側が現行のエラー通知
  経路で診断を出し、次回のユーザー操作（バッジ再クリック等）で再試行
  できること。無反応のままにしないこと。

### 4.2 Service Worker の構成

現行：起動時に計 752,066 bytes（内訳は §1.1）を同期ロード。
目標：起動時は `background.js` 本体のみとし、残りは用途別に遅延ロードする。

| ファイル | ロードタイミング（目標） |
|---|---|
| `parser.js` | 画像メタデータ解析の初回リクエスト時 |
| `png_metadata_scanner.js` | PNG と判定された初回リクエスト時（`parser.js` に依存するため、その後） |
| `video_parser.js` / `video_range_reader.js` | 動画メタデータ解析の初回リクエスト時 |
| `jszip.min.js` | ZIP ダウンロード処理の直前 |
| `pako.js`（または §5.3 の代替） | `png_metadata_scanner.js` と組でロードする（下記注記参照） |

注記：scanner は IDAT 処理でほぼ常に inflate を必要とするため、
**組としてロードするのは `png_metadata_scanner.js` + `pako.js`
（または代替）の 2 ファイル**とし、scanner をロードする際は pako を
同時にロードする（「scanner は入ったが pako がない」状態で依存エラーに
なる経路を作らないため）。`parser.js` は表のタイミングで単独に
先行ロードしてよい（JPEG 等の初回リクエストで scanner + pako まで
同時に読み込むことはしない）。

遅延ロードは「ロード済みフラグ + 初期化 Promise の共有」で冪等にし、
並行リクエストが二重に `importScripts` しないこと。ロード失敗時は診断を
現行の仕組み（`initializationState` 系の安全診断）に記録するが、失敗の
扱いは FR-SW-02 のモジュール単位分離に従い、全体 fatal にはしないこと。

### 4.3 パーサの構成

- PNG は `png_metadata_scanner.js` に一本化する。`parser.js` の
  `extractPngMetadata` および PNG 専用ヘルパ（`parsePngTextChunk` 等）は
  Phase 4 で削除し、呼び出し側は全て scanner の API
  （`scanPngMetadataBuffer` / `scanPngMetadataStream`）へ寄せる。
- 非 PNG（JPEG / WebP / AVIF / Safetensors / 動画）は現行の担当ファイルを維持する。
- 形式判定（`detectImageFormat` 等）は `parser.js` に残す。

## §5 高速化・軽快化の設計

### 5.1 content script 分割（Phase 1）

要件：

- **FR-CS-01**: 常駐注入の合計サイズ（JS + CSS）を現行 339,413 bytes から
  **120,000 bytes 以下**にする。現行の常駐区分の単純合計は約 140KB であり、
  180KB 級の目標では `content.js` の分離が実質不要になってしまうため、
  分離を実際に駆動する値として設定した。あわせて Phase 0 の B-01 で
  区分別の分離可能量を実測し、この値が構造上達成不能と判明した場合は、
  Phase 1 着手前に本書を改訂して確定値を入れ直すこと（黙って目標を
  緩めた状態で完了扱いにしない）。達成値は Phase 1 の PR に記録する。
- **FR-CS-02**: 遅延 A・B・条件付きの各ファイルは、対象場面が発生するまで
  パースも実行もされないこと。対象外サイトでは `adapters.js` が一切
  読み込まれないこと。
- **FR-CS-03**: 遅延注入後も現行の機能が全て動作すること。特に
  (a) バッジ表示とモーダル、(b) Civitai 等でのアダプタ動作、
  (c) アクション起動の全ページスキャンとダウンローダ、(d) SPA 遷移後の再検出。
  あわせて、遅延モジュールの初期化は設定ロードの完了（常駐側が持つ既存の
  ready 通知の仕組み）を待ってから行うこと。設定の実取得は非同期であり、
  注入直後にデフォルト値で初期化される競合を新たに作らないこと。
  モジュールが必要な操作（バッジクリック等）は、注入完了の応答を待ってから
  処理を継続し、**ユーザ操作 1 回で完結すること**（注入のために 2 回目の
  クリックを要する実装は不可）。
- **FR-CS-04**: URL 変化の検出から `setInterval(..., 200)` のポーリングを外す。
  `popstate` / `hashchange` と既存 MutationObserver のコールバックに連動する
  デバウンス付きチェックへ移行する。設計上の制約として、
  `history.pushState / replaceState` では `popstate` は発火せず、分離ワールドの
  content script からページ側 history をラップして傍受することもできない
  （MAIN world 注入が必要になり §4.1 の方針に反する）ため、最終保証は
  安全弁ポーリングが担う。安全弁の間隔は **800ms** とし、デバウンスは
  **100ms 以下**に固定する。検出上限は「イベント／Observer が効く遷移では
  即時、それ以外はポーリング間隔 + デバウンス + 検出処理の実行時間を含めて
  **1 秒以内**」と定義する（間隔とデバウンスの合計を 900ms に抑え、
  処理時間の余地を残す。200ms 周期と比べ、ポーリングの呼び出し回数は
  1/4 になる）。
  §11.4 の手動確認では、現行 200ms ポーリングが担っている実ケース
  （Civitai のバージョン切替等）を列挙し、そのケースで遷移後 1 秒以内に
  検出されることを基準とする。
  800ms を超える間隔への拡大と、200ms 周期の復活はともに禁止する。
- **FR-CS-05**: `all_frames: true` と `document_start` は常駐分については
  現行を維持する（バッジのちらつき防止とフレーム内画像の検出は現行仕様）。
  ただし遅延ファイルはフレーム単位で重複注入しないこと（§4.1 のフラグは
  フレームごとに持つが、同一フレームへの二重注入を防ぐこと）。
- **NFR-CS-01**: 分割によって content script 間のグローバル参照が壊れた場合は、
  参照側を遅延ロード完了後に解決する形に直すこと。`window.*` 経由の暗黙の
  読み込み順依存を新たに増やさないこと。

設計上の注意：

- 現行の読み込み順（manifest の `js` 配列順）に依存した初期化がある場合は、
  Phase 1 の中で「常駐側が持つ初期化」と「遅延側が持つ初期化」に切り分け、
  遅延側の初期化は注入直後に明示的に呼ぶ関数へ移すこと。
- 設定（`settings_loader.js`）は全区分から参照されるため常駐に残す。
- 診断（safeDiagnostic 系）の三重実装（`background.js` / `content.js` /
  `settings_loader.js`）の統合は本フェーズでは行わない（Phase 4 の対象。
  §8.3）。フェーズを跨いだ同時改修を避けるためである。

### 5.2 Service Worker の遅延ロード（Phase 2）

> **2026-11-26 仕様改訂（Phase 2 保留）**: Chrome MV3 の Service Worker は、
> 初期評価後の `importScripts()` と動的 `import()` を実行できない。
> Chromium 158 で、`fetch(chrome.runtime.getURL('parser.js'))` は 200 を返す一方、
> 起動後の `importScripts(chrome.runtime.getURL('parser.js'))` は
> `NetworkError: ... failed to load` になった。web.dev の Service Worker
> 仕様でも dynamic `importScripts()` は不可と明記されている。
>
> したがって、本節の FR-SW-01/02 が前提とする「起動後に importScripts で
> 遅延ロードする」方式は、本書のままでは実装不能である。
> **Phase 2 は方式決定まで保留**し、現行の起動時 `importScripts` を
> 暫定維持する。代替方式の詳細比較は
> `docs/phase2-sw-lazy-options.md` を正とする。
>
> - **案 A**: offscreen document へ取得・解析を移す。SW を薄いルーターに
>   でき、FR-SW-01 の 250KB 目標を達成できる可能性がある。ただし
>   `offscreen` 権限、最低 Chrome 109、取得層の移設、Phase 2 の分割が必要。
> - **案 B**: SW 遅延ロードを v2.0.0 の対象から外し、現行の起動時
>   `importScripts` を維持する。実装リスクは低いが、起動時ロードは
>   765,954 bytes のまま。
>
> 仕様改訂 PR ではこの保留と比較を記録し、実装は行わない。案の決定後に
> §4.2、FR-SW-01〜04、§13.1 を改訂する。

要件：

- **FR-SW-01**: SW 起動時に同期ロードされるのは `background.js` 本体
  （遅延ローダのコードを含む）と、Phase 4 で切り出す場合の共有診断ファイル
  のみとする。起動時ロード量の合計を現行 752,066 bytes から
  **250,000 bytes 以下**にする（ローダ追加で本体が現行 224,634 bytes から
  増える分と、共有診断ファイル分を見込んだ値）。達成値は Phase 2 の PR に
  記録し、Phase 4 の完了時にも再計測して目標内であることを確認する。
- **FR-SW-02**: §4.2 の表のタイミングで遅延ロードする。各ファイルはプロセス内で
  一度だけロードされ、並行リクエストで競合しないこと。ロード失敗は
  モジュール単位で分離し、失敗した機能のみを利用不可として再試行可能に
  すること。全体を fatal 扱いにしてよいのは起動時の必須処理の失敗に限る。
- **FR-SW-03**: 遅延ロード対象の関数を呼ぶ全ての入り口（メッセージ種別ごと）は、
  呼び出し前に必要なファイルのロード完了を待つこと。未ロード状態で
  `ReferenceError` になる経路を残さないこと（対象関数の棚卸し表を PR に添付する）。
- **FR-SW-04**: 動画メタデータ、ZIP ダウンロード、Safetensors、メタデータ
  書き込み（`rewriteImageMetadata` を使う経路）を含め、`parser.js` 等の
  遅延対象に依存する全メッセージ種別の機能が、SW 再起動直後の初回利用でも
  従来どおり動作すること。対象メッセージ種別の一覧は FR-SW-03 の棚卸し表と
  同一のものを使うこと。

### 5.3 pako の扱い（Phase 2 の後半、決定ゲート付き）

現状：`pako.js`（238,805 bytes）のうち使用しているのは、scanner の増分展開用
`pako.Inflate` と、`parser.js` の `parsePngTextChunk` が圧縮 iTXt に使う
ワンショット `pako.inflate` の 2 つであり、deflate（圧縮）側は未使用である。
spike（FR-PAKO-01）の棚卸しはこの両 API を対象とすること。代替候補は
ブラウザ標準の `DecompressionStream`：

- PNG IDAT および iTXt / zTXt の圧縮形式は zlib（`deflate`）、
  Stealth の圧縮ペイロードは gzip（`gzip`）であり、どちらも
  `DecompressionStream` の対応形式に含まれる。

進め方（ゲート）：

- **FR-PAKO-01**: まず検証（spike）として、現行テストフィクスチャの圧縮データを
  `DecompressionStream` で展開し、pako の結果とバイト単位で一致すること、
  および破損ストリーム・途中切断時のエラー挙動の差異を一覧化すること。
  この検証は使い捨てスクリプトでよいが、結果は Phase 2 の PR に記録する。
- **FR-PAKO-02**: 移行の可否は次のゲート条件で二値に判定する。**全てを
  満たす場合にのみ移行し、1 つでも満たさなければ中止する**：
  (a) scanner の公開 API の同期性が維持できる、または非同期化の影響範囲が
  scanner 内部とその直接の呼び出し側に閉じ、かつ必要なテスト変更が
  §11.3 に先行して追加されていること；
  (b) 破損・切断時の診断カテゴリが現行と一致すること；
  (c) **全ての置換経路で、展開後バイト数の逐次計数と上限到達時の abort を
  維持できること**（`DecompressionStream` 自体には出力上限の仕組みがない。
  現行の `MAX_TEXT_CHUNK_BYTES` / `MAX_STEALTH_METADATA_BYTES` 等の上限を
  迂回して一括受信する実装は、展開爆弾への耐性を落とすため禁止する）；
  (d) §11.2 Phase 2 のテストが移行後も同等の検証密度を保てること。
  移行した場合は `pako.js` をリポジトリから削除する。
- **FR-PAKO-03**: ゲート条件を満たさない場合は移行を中止し、現行 `pako.js` を
  維持する。その場合も §4.2 の組ロード（scanner と同時）による遅延ロード
  （FR-SW-02）は適用する。中止の判断と、満たさなかった条件は
  PR に記録し、本書 §3 に CUT 項目として追記する PR を別途出すこと
  （あわせて付録 A の ID 一覧の範囲表記も更新すること）。
> **2026-11-26 決定（FR-PAKO-01/02）**: `docs/pako-gate-phase2.md` の検証により、
> 有効データの出力は pako と `DecompressionStream` でバイト一致したが、
> (a) scanner / parser の同期 API を維持できず、(b) 破損・切断時の診断カテゴリも
> 一致しないため、移行を中止する（FR-PAKO-03）。`pako.js` は維持し、§3 に
> CUT-13 を追加する。scanner との組ロードは Phase 2 の方式決定後に再評価する。

- **禁止事項**: pako の inflate-only カスタムビルドを生成して vendor し直すことは、
  生成手順の再現性が本書で管理できないため行わない（CUT-10 の精神による）。
- 注記：棚卸し対象のうち `parser.js` の `parsePngTextChunk` は Phase 4 で
  削除されるため、その分の置換は Phase 4 までの暫定対応になる。移行コストの
  評価（FR-PAKO-02 のゲート判定）にはこの暫定分を含めること。

## §6 検知追加の仕様（全てゲート付き、Phase 3）

共通規則：

- **FR-DET-00a**: 追加する担体はいずれも、既存の走査の「通り道」で判定でき、
  新規のネットワーク取得を発生させないこと（P-2 の A またはゲート付き B）。
- **FR-DET-00b**: 追加担体で得た値は、既存担体の値を上書きしない。
  優先順位は「既存担体（PNG tEXt/iTXt/eXIf、JPEG EXIF、WebP EXIF/XMP）＞
  本節で追加する担体」とし、キーが重複した場合は既存側を残す。
- **FR-DET-00c**: 追加担体の parserState への影響は既存担体と同じ規則に従う。
  追加担体のみが存在し内容ゲートを通った場合は `resolved`、ゲートで棄却した
  場合は「担体がなかった」ものとして扱い、他の担体の確定状態を変えない。
- **FR-DET-00d**: 各担体には §11 のテストを必須とする。フィクスチャは
  テストコード内でバイト列を組み立てる現行方式に従い、バイナリファイルの
  追加は行わない。
- **FR-DET-00e（表示時サニタイズ）**: 追加担体および §9 の新規セクションで
  得た値は全て Web 由来の不信データである。表示は既存のテキスト描画経路
  （`textContent` 等のエスケープが効く経路）を通し、`innerHTML` へ直接
  渡してはならない。§11.2 にエスケープ確認のテストを必須とする。
- **FR-DET-00f（キャッシュ版数の更新）**: 本節の追加は検出結果を変えるため、
  Phase 3 の完了時に `PNG_SCANNER_CACHE_VERSION` と
  `PARSER_CACHE_VERSION` の該当する方（PNG 担体は前者、非 PNG 担体は後者、
  両方に触れる場合は両方）を更新すること。版数を上げないと、アップグレード
  直後のユーザには旧 negative cache（empty-confirmed）が効き続け、
  新担体が表示されなくなる。

### 6.1 PNG zTXt（ゲート付き）

対象箇所：`png_metadata_scanner.js`（一本化後の PNG 唯一の実装。Phase 3 は
Phase 4 より前に実施するため、この時点では scanner 側にのみ実装し、
`parser.js` の旧 `extractPngMetadata` には実装しない。旧実装は Phase 4 で
削除される。§13.1 のフェーズ順序の理由を参照）。

仕様：

- **FR-ZTXT-01**: チャンク種別 `zTXt` を認識する。キーワードは圧縮されていない
  先頭部（最初の NUL まで）から読み、以下の許可リストに一致する場合にのみ
  本文を inflate する。**許可リストはこの 8 語で確定とし、追加は本書の
  改訂事項とする**（現行 scanner の tEXt 処理には許可リスト自体が存在せず
  「同一の集合」は導出できないため）：
  `parameters`, `prompt`, `workflow`, `generation_data`, `Comment`,
  `Description`, `Software`, `Source`。
  展開後の本文のデコード方法は、現行 scanner の tEXt 本文と同一とする。
- **FR-ZTXT-02**: 許可リスト外の zTXt は、現行の対象外チャンクと同様に
  チャンク長でスキップする。本文のバッファリングも inflate も行わない。
  これを現行 scanner の状態機械（チャンク全体を確保してからパースする方式）
  で実現するため、次の先読み設計を §6.1 の一部として実装すること：
  チャンクデータの先頭から「キーワード + NUL + 圧縮方法バイト」が揃うまでを
  小さな先読みバッファ（キーワードの形式上の最大長から **128 bytes** を上限
  とする）で受け、push 境界を跨ぐ場合もこの範囲で判定する。キーワードが
  許可外と確定した時点で先読み分を解放し、残りは確保せずスキップへ移行する。
  また圧縮本文長（チャンク長からキーワード部を引いた値）が FR-ZTXT-04 の
  入力上限を超える zTXt は、キーワードが許可リスト内でも確保しない。
  先読みバッファ 128 bytes 以内に NUL が確定しない場合は、現行 tEXt の
  キーワード文法違反と同一の棄却・診断とし、残部はチャンク長でスキップする。
- **FR-ZTXT-03**: 圧縮方法バイトが 0（zlib）以外の zTXt は棄却する。
- **FR-ZTXT-04**: 上限値：圧縮本文の入力上限は **2MB**、展開後上限は
  **8MB**（現行 `MAX_TEXT_CHUNK_BYTES` と同じ）とする。超過時の扱いは
  両上限とも「診断（resource-limit 系）を出して当該 zTXt を棄却」とし、
  無言スキップにはしない（FR-ZTXT-02 の「確保しない」はバッファ確保の
  禁止を指し、棄却時の診断を免除するものではない）。メタデータ全体を
  失敗にしない。
- **FR-ZTXT-05**: inflate は §5.3 の結果に従い、その時点で有効な実装
  （pako または DecompressionStream）を使うこと。zTXt のためだけに
  別の inflate 経路を作らない。
- **FR-ZTXT-06**: CRC の扱いは他のテキストチャンクと同一とする。

### 6.2 JPEG COM セグメント（内容ゲート付き）

対象箇所：`parser.js` の `scanJpegMarkers`。

仕様：

- **FR-COM-01**: マーカー `0xFFFE`（COM）を認識し、SOS 到達前までの走査範囲内で
  処理する。SOS 以後には入らない（CUT-03）。
- **FR-COM-02**: 内容ゲート：COM の本文（**UTF-8 としてデコード**する。
  デコード失敗時は現行の EXIF 系の失敗時挙動に倣う）が次のいずれかを
  満たす場合にのみメタデータとして採用する。
  (a) 先頭が `{` で始まり JSON として解釈でき、生成情報らしいキー
  （`prompt` / `workflow` / `parameters` のいずれか）を含む、
  (b) A1111 形式の特徴を持つ。すなわち `Negative prompt:` を含む、または
  `Steps:` と（`Sampler:` / `Seed:` / `CFG scale:` / `Size:` のいずれか）が
  共存する（単独の `Steps:` 行だけでは手順説明コメント等と区別できないため
  ゲートを通さない）。
  なお旧案にあった「自前書き込み形式との一致」はゲートとして成立しない
  （`writeJpegMetadata` は COM に識別マーカーを持たないプレーンテキストを
  そのまま書くため、任意のテキストとの区別がつかない）ので採用しない。
  代わりに書き手側の制約とし、自前書き込みで COM に書く本文は (a) または
  (b) を満たす形式であること（現行の書き込み内容は A1111 形式であり (b) を
  満たす）。メタデータ編集機能でユーザが任意テキストに書き換えた場合、
  その本文が (a)/(b) を満たさなければ読み直し時に採用されない。これは
  既知の制約として仕様に明記する（書き込み時の警告表示は行わない）。
  ゲート不通過の COM は一般コメントとして無視し、parserState に影響させない。
  既存テスト「JPEG ignores EXIF-like bytes in an unrelated comment segment」の
  期待結果（無関係な COM は空確定のまま）は維持すること。
- **FR-COM-03**: 採用した COM はキー `parameters` として格納する。
  ただし EXIF 由来の `parameters` が既にある場合は FR-DET-00b により
  EXIF 側を優先し、COM 側は破棄する。
- **FR-COM-04**: COM 本文の上限はセグメント構造上の最大（65,533 バイト）で
  足りるため追加の上限は設けない。ただし複数 COM がある場合は最初に
  ゲートを通ったものだけを採用し、残りは走査のみで保持しない。

### 6.3 JPEG APP1 XMP（ヘッダゲート付き）

対象箇所：`parser.js` の `scanJpegMarkers`。WebP XMP との非対称
（WebP では拾うのに JPEG では拾えない）の解消が目的である。

仕様：

- **FR-JXMP-01**: APP1 セグメントのうち、先頭が XMP 名前空間識別子
  `http://ns.adobe.com/xap/1.0/\0` で始まるものを XMP として処理する。
  EXIF の APP1（`Exif\0\0`）との判定は先頭バイトで行い、混同しないこと。
- **FR-JXMP-02**: XMP 本文は既存の `parseXmpMetadata`（§6.6 の改善後）へ渡す。
  得られた `parameters` / `Description` は FR-DET-00b の優先順位に従う。
- **FR-JXMP-03**: Extended XMP（`http://ns.adobe.com/xmp/extension/\0`）は
  対象外とする（CUT-05）。識別子を見たらスキップし、未対応であることを
  理由に `unresolved` へ倒さない（XMP 本体が読めていれば確定状態は
  本体に従う。本体もない場合は従来どおりの判定に委ねる）。
- **FR-JXMP-04**: XMP 本文が head budget の範囲で切り取られた場合は、
  既存 EXIF の切り取り時と同様に `unresolved` / `metadataPartial` の
  規則に従う。新規の再取得ロジックは作らない。

### 6.4 PNG trailing（取得済みデータへの相乗り限定）

対象箇所：`png_metadata_scanner.js` の stream / buffer 両経路。

仕様：

- **FR-TRL-01**: IEND 到達後、**既に手元にあるバイト列の範囲内でのみ**
  trailing を検査する。trailing のために Range 取得・tail fetch・full fetch の
  いずれも新たに発生させてはならない（CUT-04）。stream 経路では現行 scanner が
  IEND で reader を cancel するため、対象は **IEND と同一の push チャンク内に
  既に受信済みの残バイトに限る**。IEND 到達を理由にストリームの読み取りを
  継続させない（現行の「IEND 後の suffix 転送を継続させない」挙動を維持する）。
  したがって stream 経路の trailing はチャンク境界に依存するベストエフォート
  であり、確定的に効くのは buffer 経路であることを仕様として明記する。
- **FR-TRL-02**: trailing の解釈はチャンクフレーミング（長さ + 種別 + 本文 + CRC）が
  完全に成立するチャンク列に限る。ここで「成立」には **CRC 値の検証**を含み、
  CRC 不一致の trailing チャンクは本体側のテキストチャンクと同様に棄却する。
  対象種別は tEXt / iTXt / zTXt（§6.1 のゲート適用後）/ eXIf とする。
  対象外種別（IDAT、IHDR 等）のチャンクは内容を解釈せず、フレーミングが
  成立する限りスキップして走査を継続する（FR-TRL-03 の上限の範囲内）。
  CRC 検証を必須とするのは解釈対象種別のみとし、対象外種別は長さ
  フィールドによるスキップのみで、CRC 不一致でも走査を止めない
  （読まないデータに CRC 計算を課さないため）。
  trailing の eXIf には本体側と同じ prefix 上限（現行
  `MAX_EXIF_CHUNK_PREFIX_BYTES` = 64KB）を準用する。フレーミングが成立しない
  バイト列へのパターン検索（文字列の出現位置探し）は行わない。
- **FR-TRL-03**: trailing として検査する上限は IEND 後 **1MB** までとする。
  上限を超えた分は検査せず、診断にも失敗にもしない。
- **FR-TRL-04**: trailing から得た値は FR-DET-00b の優先順位で最も低い
  （本体チャンクが優先）。trailing の有無は IEND までの本体の確定状態
  （valid-iend 等）を変えない。現行テストの「IEND 後のチャンク出現は
  構造エラー」という期待とは衝突するため、当該テストは本フェーズで
  「本体としては IEND で正常終了し、trailing は別枠で解釈する」仕様へ
  更新してよい（§11.3 の変更許可リストに明記する）。

### 6.5 EXIF 収穫タグの追加（Software のみ）

対象箇所：`parser.js` の `extractExifMetadata`。

仕様：

- **FR-EXIF-01**: 収穫タグに `0x0131 Software` を追加し、キー `Software` として
  格納する。値の上限は既存の `EXIF_MAX_VALUE_BYTES` の枠内で、文字列として
  採用するのは **256 バイト以下**のものに限る（生成元判定のための短い
  識別子であり、長い値は生成情報ではないため）。
- **FR-EXIF-02**: それ以外のタグ追加は行わない（CUT-07）。特に
  ImageDescription（0x010E）と UserComment（0x9286）の既存処理は変更しない。
- **FR-EXIF-03**: 本計画では `Software` の格納までを行う。表示・生成元判定への
  利用は本計画の対象外とし、将来課題（§14）とする（§9 の Phase 6 は
  InvokeAI / SwarmUI の解釈のみであり、Software の利用要件は含まない）。

### 6.6 XMP パーサの限定的改善

対象箇所：`parser.js` の `parseXmpMetadata`。CUT-11 の範囲内で、
文字列レベルの取りこぼしだけを直す。

仕様：

- **FR-XMP-01**: 次の 4 点に対応する：
  (a) CDATA セクション（`<![CDATA[ ... ]]>`）で包まれた `parameters`
  （採用する値からは CDATA マーカー自体を除去すること）、
  (b) 属性値の単一引用符形式（`parameters='...'`）、
  (c) 16 進数値文字参照（`&#x....;`）と `&apos;` のデコード、
  (d) `parameters` タグ形式における名前空間接頭辞の有無の両対応。
- **FR-XMP-02**: 既存のデコード順序は維持する。なお現行順序
  （`&quot; → &lt; → &gt; → &amp; → &#10; → &#13;`）は `&amp;` の後に
  数値参照を処理するため、`&amp;#10;` が改行に化けるような二重デコードが
  現行でも起こり得る。これは既存挙動として本計画では変更しない。
  新規デコード（16 進参照、`&apos;`）については既存分と扱いを分ける。
  新規分には互換性の理由がないため、既知の二重デコードを拡大させない：
  `&amp;` でエスケープされた形（`&amp;#x....;` 等）が新規デコードで
  展開されない実装とし、二重デコードが起きないことをテストで固定すること。
  既存テストの期待値は変えないこと。
- **FR-XMP-03**: 正規表現の壊滅的バックトラッキングが起きないこと。
  入力は最大で head budget 由来の 256KB 級になり得るため、入れ子量指定子の
  ある正規表現を追加しないこと。

## §7 Stealth の切り捨てと二段化（Phase 5）

### 7.1 現状と問題

現行 scanner は、通常メタデータが見つかった後も IDAT の検証を継続し、
画素展開を伴う処理が大容量 PNG で支配的になるケースがある（§1.1）。
Stealth の出現率は通常メタデータよりさらに低く、「Stealth がないことの確認」に
全画素展開を払うのは P-1 に反する。本節はその切り捨てを仕様化する。

なお効果にはチャンク順序への依存がある。IDAT より前にテキスト／eXIf
チャンクがあるレイアウトでは「メタデータ確定後に IDAT 検証をやめる」効果が
出るが、IDAT が先行するレイアウトでは確定時点で展開が終わっており効果は
ほぼない。Phase 0 の B-04 では両順序のフィクスチャを分けて計測すること。

### 7.2 二段化の仕様

- **FR-STL-01（第 1 段：署名判定）**: Stealth 候補の処理は、先頭の署名判定に
  必要な行範囲（現行 `MAX_STEALTH_HEADER_ROWS` 相当）までで一旦確定させる。
  署名が不一致（候補 rejected）になった時点で、その候補の画素処理は終了する。
  これは現行の早期停止の延長であり、挙動を仕様として明記するものである。
  本計画では現行定数 `MAX_STEALTH_HEADER_ROWS` の値そのものは変更しない
  （署名確定に必要な範囲は現行実装の定数を正とする）。
- **FR-STL-02（第 2 段：全展開）**: 署名が一致（matched）した候補についてのみ、
  ペイロード読み取りのための全展開に進む。matched にならなかった画像では
  IDAT の画素展開は第 1 段の範囲を超えて行わない。
- **FR-STL-03（通常メタデータ優先）**: tEXt / iTXt / zTXt / eXIf のいずれかから
  通常メタデータが確定した画像では、Stealth 候補処理を行わない（現行の
  `suppressStealthForNormalMetadata` を、IDAT 展開開始前にも効くよう拡張する）。
  この場合の IDAT 検証は「チャンクフレーミングと、圧縮バイト列に対する CRC」の
  範囲に留め、**zlib ストリームの展開検証と展開後サイズ検証は行わない**。
  したがって「EXIF あり + IDAT の zlib が破損」は今後 `invalid-png` ではなく
  正常（メタデータあり）として返る。これは意図的な仕様変更であり、
  更新対象になるのは zlib 展開検証・展開後サイズ検証に由来する期待値のみで、
  §11.3-1 の許可範囲に従って更新すること。チャンク CRC の不一致は
  従来どおり検出対象とする（CRC は圧縮バイト列から計算でき、C に該当しない）
  ため、chunk CRC を扱う現行テスト（"PNG reports invalid IDAT CRC even when
  EXIF metadata was already found"）は**無変更で通ることが Phase 5 の
  確認条件**であり、その期待値を弱めてはならない。
- **FR-STL-04**: 通常メタデータがなく Stealth 候補も rejected の画像では、
  残りの IDAT についてはフレーミング走査（チャンク長でのスキップ）に切り替え、
  後続チャンク（IEND 前のテキストチャンク等）の検出は継続する。
  現行テスト "PNG stops Stealth candidate work after rejection..." の
  期待（後続 tEXt が読めること）は維持すること。
- **FR-STL-04b（検証を落とすケースの完全な列挙と下流影響）**: zlib 展開検証
  （ストリーム終端・展開後サイズ一致）を落としてフレーミング走査に切り替える
  のは、次の 3 ケース全てとする。これ以外のケースでは現行の検証を維持する：
  (i) 通常メタデータが確定した画像（FR-STL-03）、
  (ii) Stealth 候補が rejected になった画像（FR-STL-04）、
  (iii) Stealth 候補が作られない画像（対象外レイアウト、インターレース、
  FR-STL-05 の上限超過を含む）。
  3 ケース共通で、チャンク CRC（圧縮バイト列に対する検証）は引き続き行い、
  CRC 不一致は従来どおり `invalid-png` とする。一方 zlib 破損のみの画像は、
  従来の `invalid-png` から「IEND 到達なら not-found（empty-confirmed）」へ
  分類が変わる。これにより当該ファイルが negative cache の保存対象になり
  得るが、これは意図したトレードオフとして許容し、移行時の旧キャッシュは
  FR-STL-07 の版数更新で無効化する。各ケースの status / parserState /
  キャッシュ可否の変化表を Phase 5 の PR に添付すること。

### 7.3 規模による切り捨て

- **FR-STL-05**: Stealth 候補処理の対象は、画素数が **33,554,432
  （2^25、約 33.5MP）以下**の画像に限る。これを超える画像では候補自体を
  作らず、診断に `unsupported-stealth` 系の記録を残してテキストチャンク等の
  通常検出のみ行う（CUT-12）。
- **FR-STL-06**: 展開全体の安全上限（現行 `MAX_DECODED_BYTES` 512MB）は
  安全弁として維持する。FR-STL-05 と二重に効くことを意図しており、
  片方を外す変更は行わない。
- **FR-STL-07（キャッシュ版数）**: 本節（§7.2・§7.3）は検出結果と分類を
  変えるため、Phase 5 の完了時に `PNG_SCANNER_CACHE_VERSION` を更新する
  こと（FR-DET-00f と同じ理由）。
- **決定ゲート**: Phase 5 の着手前に、Phase 0 で用意した実測（§10）に基づき
  上限値 33.5MP の妥当性を確認する。手元の実例（NovelAI 等の Stealth 画像は
  通常 1〜3MP 級、アップスケール後でも 4K＝約 8.3MP 級）に照らして十分な
  余裕がある想定だが、実例が上限に近い場合は上限値を引き上げて本書を
  改訂してから着手すること。上限値を下げ方向に変える改訂は禁止する
  （検出率を実測なしに落とさないため）。B-06 で実例が得られず合成 Stealth
  で代替した場合は、実測に基づく検証は不能である旨と、33.5MP を暫定値として
  採用した旨を Phase 5 の PR に記録することをゲートの完了条件に加える。

### 7.4 対象外の Stealth 仕様

- インターレース（Adam7）は対象外のまま（CUT-01）。現行の
  `unsupported PNG stealth layout` 診断を維持する。
- 対応カラータイプ／ビット深度の拡張は行わない。現行 `LAYOUTS` の範囲が正である。
- Stealth の書き込み（埋め込み）機能は本計画の対象外である。

## §8 保守性リファクタ（Phase 4）

### 8.1 PNG パーサ一本化

- **FR-UNI-01**: §4.3 のとおり `parser.js` の PNG 一括実装を削除し、全経路を
  scanner に統一する。削除対象には `extractPngMetadata`、`parsePngTextChunk`、
  および PNG 専用と確認できたヘルパを含む。削除前に呼び出し箇所の棚卸しを行い、
  `background.js` の fallback 経路を含め全て scanner 経由に置換すること。
- **FR-UNI-02**: 一本化で検出結果が変わってはならない。比較の基準は
  **Phase 4 着手直前の scanner の出力**とし、入力には Phase 0 の等価性
  フィクスチャ（B-05）を再利用する。一本化の前後でメタデータの内容と
  parserState が一致すること。Phase 0 時点の旧 `extractPngMetadata` との
  差異は、Phase 3 で意図的に追加された担体（zTXt / trailing 等）による
  ものとして一覧化し、一致を要求しない。差異が出た場合は scanner 側の
  挙動を正とし、差異の一覧と理由を PR に記録すること。
- **FR-UNI-03**: CRC の増分 API（`createCrc32State` 等、scanner が依存する
  `parser.js` 側公開関数）は一本化後も維持する。scanner の依存チェック
  （`PngScannerDependencyError`）が通ることを確認すること。

### 8.2 キャッシュの小修正

- **FR-CACHE-01**: `PersistentLRUCache.clear()` の `storage.local.clear()`
  （全体消去）を、接頭辞 `meta_cache_` を持つキーと index キーのみの
  `remove` に変更する。実装方法は「`storage.local.getKeys()`（キー名のみを
  返す API）が使える環境ではそれで列挙し、使えない場合のフォールバック
  としてのみ `get(null)` を許容する」こと（キー列挙のためだけに最大約 4MB の
  キャッシュ値全体を実体化させない）。キャッシュ以外の local データを
  消してはならない。なおクリア実行と並行して進行中の解析が完了し、
  クリア後に結果が再登録されることは許容する（仕様として明記し、
  競合を潰すためのロックは導入しない）。
- **FR-CACHE-02**: `ensureCapacity` の全件ソートを、Map の挿入順
  （最も古いエントリが先頭）を利用した走査に置き換える。追い出しの結果
  （どのエントリが消えるか）が現行と同等であることをテストで示すこと。
  なおアクセス時の順序更新（真の LRU 化）は行わない。現行は FIFO であり、
  本修正はその意味論を変えない範囲に留める。
- **FR-CACHE-03**: キャッシュキーの URL 正規化（クエリ除去やハッシュ化）は
  本計画では行わない。キー形式を変えると既存キャッシュが無効化され、
  移行の検証コストが見合わないためである（将来課題として §14 に記す）。

### 8.3 その他の重複整理

- **FR-DUP-01**: safeDiagnostic 系の三重実装は、共有ファイルへの切り出しを
  行う。ただし content script 側は §4.1 の常駐区分に置く必要があり、
  background 側は SW のグローバルで読める必要がある。両環境でそのまま
  読める単一ファイル（モジュール構文なし）として切り出し、読み込み順は
  manifest と `importScripts` の双方で先頭側に置くこと。
- **FR-DUP-02**: `TextDecoder` の生成を共有定数化する（`parser.js` /
  `png_metadata_scanner.js` 内の繰り返し生成箇所）。`fatal: true` など
  オプションが異なる箇所は別定数とし、挙動を変えないこと。
  `slice()` によるコピーは、寿命が安全な箇所に限り `subarray` へ置換する。
  効果測定が目的ではなく保守と GC 圧の低減が目的なので、置換は保守的に行い、
  迷う箇所は現行維持とする。

### 8.4 background.js の分割について

- **FR-BG-01**: `background.js`（4,846 行）のファイル分割そのものは本計画では
  行わない。§5.2 の遅延ロードで起動コストの問題は解消されるため、
  分割はリスク（初期化順序、グローバル共有の崩壊）に対して利益が薄い。
  ただし §5.4 で許可した範囲の変更と、FR-DUP-01 の切り出しは行う。
  分割は将来課題（§14）とする。

## §9 生成元解釈の追加（Phase 6、positive 限定・任意）

本フェーズは P-4（positive 限定コストは許容）に基づく。メタデータが既に
取得できた画像の表示時にのみ動作し、取得コストには影響しない。
優先度は最も低く、Phase 1〜5 の完了を妨げない。v2.0.0 への同梱は任意とし、
遅れる場合は独立したマイナーリリースに分離してよい。

- **FR-GEN-01**: `ui.js` の `detectGenerator` とセクション整形に、次を追加する。
  いずれも「キーは既に汎用取得で入ってくるが解釈がない」ものに限る。
  なお当該キーが取得できるのは現行では PNG の tEXt 経路に限られる
  （JPEG / WebP には当該キーの取得経路自体がない）。本フェーズは表示側の
  解釈追加のみとし、他形式への取得追加は §6 の範囲外として行わない：
  - InvokeAI：キー `invokeai_metadata`（JSON）と旧形式 `sd-metadata`（JSON）。
    JSON 内の prompt / negative 等を表示用セクションへ振り分ける。
  - SwarmUI：キー `sui_image_params`（JSON）。prompt / negative_prompt /
    model 等を振り分ける。
- **FR-GEN-02**: Fooocus / Easy Diffusion / Draw Things は、実例フィクスチャが
  用意できたものだけを追加する。用意できないものは本フェーズでも追加しない。

  「持たない画像に重い処理をしない」形に限る（P-1 / P-2）。
- zTXt は AI PNG での出現がほぼなく優先度は低いが、キーワードゲートにより
  negative コストをほぼゼロにできるため、ゲート付きで採用した（§6.1）。
- JPEG COM は生成情報の担体としての出現はほぼないが、走査の通り道にあり
  内容ゲートで誤検出を防げるため採用した。自前書き込みとの整合は、
  読み手に識別マーカーがない以上ゲートにはできないため、書き手が
  内容ゲートを満たす形式で書くことで取る（§6.2）。
- trailing は、追加取得を伴う形では却下し、取得済みデータへの相乗りのみ
  採用した（§6.4 / CUT-04）。Stealth の全量取得が苦渋の判断であったのと
  同じ構造である。
- Adam7 Stealth と新形式（JXL 等）は、出現率とコストの両面から却下した
  （CUT-01 / CUT-02）。
- JPEG の 256KB budget と SOS 打ち切りは、苦渋ではなく現行が妥当と
  判断した（CUT-03）。
